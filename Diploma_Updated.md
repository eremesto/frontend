# StoHelper — Обновлённая версия диплома

Ниже приведён актуализированный текст ключевых разделов дипломной работы, отражающий реализацию фронтенда и бэкенда проекта StoHelper.

---

## Введение

В последние годы цифровые технологии всё активнее входят в сферу услуг, преобразуя традиционные процессы взаимодействия клиента и исполнителя. Анализ практики показывает, что в сегменте автосервисов широко распространены устаревшие методы организации записи и коммуникации: телефонные звонки, мессенджеры и ручной учёт. Такая модель работы не только снижает качество обслуживания, но и увеличивает операционные расходы, поскольку существенно возрастает вероятность ошибок, дублирования заявок и потери истории взаимодействия.

Актуальность работы. Развитие мобильных приложений как основного канала для взаимодействия с пользователями обуславливает потребность в доступных, лёгких в развёртывании решениях для малого и среднего бизнеса. Одна из приоритетных задач — интеграция поиска автосервисов, бронирования слотов и управляемой переписки в одном приложении, что позволяет снизить зависимость от внешних мессенджеров и обеспечить прозрачность процесса обслуживания.

Цель работы. Разработать прототип мобильного приложения StoHelper и соответствующий серверный REST API, обеспечивающие поиск автосервисов по услугам, выбор даты и времени, резервирование слотов, управление заявками и обмен сообщениями внутри заявки.

Новизна работы. В рамках проекта реализован комплексный подход, сочетающий клиентскую мобильно-ориентированную архитектуру и лёгкий серверный API. Использован механизм одноразовой email-верификации с временным токеном, а также оптимистичная отправка сообщений и периодический опрос сервера (polling) для синхронизации данных при ограниченных ресурсах бэкенда.

Методы и средства. В работе применены методы прототипирования, инженерного проектирования и программной реализации. Клиент выполнен на React Native / Expo с TypeScript, Redux Toolkit и RTK Query; сервер — на Node.js/Express с MongoDB/Mongoose; для обеспечения безопасности и валидации применены express-validator, bcryptjs и jsonwebtoken.

Структура работы. Документ содержит обзор предметной области, системный анализ, архитектурное проектирование, описание реализации клиентской и серверной частей, план тестирования и инструкции по развёртыванию.

## Постановка задачи

Общая цель: разработать и реализовать рабочее прототипное решение — мобильное приложение и серверную часть — обеспечивающее поиск автосервисов, бронирование услуг и обмен сообщениями по заявке.

Задачи, решаемые в рамках работы:
- спроектировать архитектуру клиент-серверного приложения;
- реализовать мобильный клиент на React Native с основными экранами: авторизация/регистрация, каталог услуг, результаты поиска, профиль, список заявок, чат;
- реализовать REST API на Node.js/Express для управления пользователями, автосервисами, заявками и сообщениями;
- обеспечить подтверждение регистрации через email-код и временный `tempToken`;
- реализовать механизм блокировки занятого временного слота и синхронизацию статуса заявки между сервисом и пользователем;
- реализовать механизм уведомления о непрочитанных сообщениях (бейджи) и периодическое обновление данных (polling);
- подготовить документацию по установке и план тестирования.

Ограничения и допущения:
- в рамках диплома не реализована онлайн-оплата и геолокационные функции;
- используется polling вместо WebSocket для упрощения серверной части;
- предполагается наличие отдельного сервера MongoDB.


## Раздел 1. Бизнес-анализ и анализ предметной области

### 1.1 Анализ предметной области

Владельцы автомобилей часто вынуждены искать автосервисы через поисковые системы, карты и мессенджеры одновременно. Это приводит к потере времени, сложности согласования услуги и неэффективному общению. Малые автосервисы чаще всего не имеют собственной цифровой платформы и принимают заявки через звонки или мессенджеры, что затрудняет учёт заявок и коммуникацию.

Проект StoHelper решает эту задачу путем создания единой мобильной платформы для клиентов и автосервисов. Система предоставляет:
- регистрацию пользователя и автосервиса;
- поиск автосервисов по категориям услуг;
- выбор даты и времени записи;
- обмен сообщениями в рамках заявки;
- управление заявками: просмотр, отмена, отметка как выполненной;
- индикаторы непрочитанных сообщений.

Приложение реализовано по клиент-серверной архитектуре:
- мобильный клиент на React Native / Expo;
- бекенд на Node.js / Express;
- база данных MongoDB с ODM Mongoose.

---

### 1.1.1 Глоссарий

- **Пользователь** — владелец автомобиля, зарегистрированный в системе.
- **Автосервис (СТО)** — организация, зарегистрированная в системе.
- **Заявка** — запись клиента на услугу с датой/временем.
- **DeclarationId** — уникальный идентификатор заявки, используемый как идентификатор в чате.
- **Слот времени** — 15-минутный интервал, доступный для бронирования.
- **Статус заявки** — состояние заявки: `active` (активна) или `done` (выполнена).
- **Polling** — периодический опрос сервера для получения новых данных.
- **Badge** — числовой индикатор непрочитанных сообщений.
- **Redux Store** — централизованное хранилище состояния.
- **Slice** — часть состояния Redux Toolkit с редьюсерами и действиями.
- **Props** — свойства компонентов React для передачи данных.
- **RTK Query** — инструмент Redux Toolkit для упрощённой работы с API-запросами.
- **Mongoose** — библиотека для работы с MongoDB и описания схем.
- **tempToken** — JWT-токен, выдающийся после подтверждения email на этапе регистрации.
- **VerificationCode** — модель для одноразового кода верификации email.

## 1.5 Моделирование предметной области

### 1.5.1 Бизнес-сущности и жизненные циклы

Основные сущности:
- пользователь;
- автосервис;
- заявка;
- сообщение;
- услуга;
- код верификации.

Ниже приведены подробные жизненные циклы ключевых сущностей с учётом моделей и реализаций на сервере.

Центральной сущностью предметной области является Заявка (Declaration). Её жизненный цикл:
- Создана (`active`) — пользователь оформил запись; заявка появляется у обеих сторон.
- В работе (`active`) — сервис принял заявку, ведётся переписка в чате.
- Выполнена (`done`) — сервис отметил заявку выполненной; статус синхронизируется у пользователя.
- Отменена — пользователь отменил заявку; запись удаляется из системы у обеих сторон.

Жизненный цикл пользователя:
- Незарегистрированный — пользователь только начал процесс регистрации.
- Зарегистрированный — email подтверждён, временный `tempToken` получен.
- Авторизованный — пользователь вошёл в систему с помощью `/user/loginUser`.
- Имеет активные заявки — пользователь создал заявку, она отображается в личном кабинете.
- Нет активных заявок — все заявки завершены или отменены.

Жизненный цикл сообщения в чате:
- Отправлено (`readBy = [senderLogin]`) — сообщение создано клиентом и сохранено на сервере.
- Доставлено — сообщение доступно получателю в истории чата.
- Прочитано (`readBy` содержит логин собеседника) — при запросе `/chat/messages/:applicationId?login=...` сервер помечает сообщение как прочитанное.

Жизненный цикл автосервиса:
- Не зарегистрирован — сервис не создан в системе.
- Зарегистрирован — сервис прошёл регистрацию через `/service/registrationAutoService`.
- Активен — сервис доступен для поиска и получения заявок.
- Заблокирован/закрыт — сервис временно недоступен или удалён из каталога.

Жизненный цикл кода верификации:
- Выдан (`issued`) — клиент запросил код через `/verification/send-code`.
- Использован (`used`) — код подтверждён через `/verification/confirm-code` и сформирован `tempToken`.
- Истёк (`expired`) — срок действия TTL завершился, код недействителен.
- Отозван (`revoked`) — код удалён вручную или при подозрении на компрометацию.

Для всех сущностей реализованы базовые механизмы валидации и синхронизации данных между клиентом и сервером, что обеспечивает корректный переход состояний и сохранение целостности бизнес-логики.

# Раздел 2. Системная аналитика и архитектурное проектирование

## 2.1 Анализ требований

### 2.1.1 Диаграмма прецедентов

Актёры:
- пользователь;
- автосервис.

Прецеденты пользователя:
- регистрация;
- авторизация;
- поиск услуг;
- бронирование;
- просмотр заявок;
- чат;
- отмена заявки;
- просмотр профиля.

Прецеденты автосервиса:
- регистрация сервиса;
- авторизация;
- просмотр заявок;
- ответ клиенту в чате;
- отметка заявки выполненной;
- редактирование профиля.

### 2.1.2 Ключевые сценарии

Сценарий «Бронирование услуги»:
1. пользователь авторизован;
2. выбирает услуги на экране `Services`;
3. попадает на `SearchResults`;
4. выбирает сервис и дату;
5. `SearchResults` запрашивает `/service/getBookedSlots`;
6. выбирает время;
7. отправляет заявку на `/service/sendApplication`;
8. сохраняет заявку у пользователя `/user/addMyApplication`;
9. заявка появляется в списке заявок.

Сценарий «Чат по заявке»:
1. пользователь/сервис нажимает кнопку чата;
2. открывается `Chat.tsx`;
3. `Chat` загружает историю через `GET /chat/messages/:applicationId?login=...`;
4. сервер помечает входящие сообщения прочитанными;
5. отправка сообщения выполняется через `POST /chat/send`;
6. сообщение появляется оптимистично до подтверждения сервера;
7. бейджи непрочитанных обновляются через `POST /chat/unread`.

### 2.1.3 Иерархический список требований

Функциональные требования:
1. Система должна обеспечивать раздельную регистрацию пользователей и автосервисов.
2. Система должна подтверждать регистрацию пользователя и сервиса через email-код и временный `tempToken`.
3. Система должна поддерживать авторизацию по логину и паролю для пользователя и автосервиса.
4. Система должна отображать только доступные временные слоты для бронирования.
5. При бронировании слот должен блокироваться для других пользователей.
6. Система должна поддерживать переписку между клиентом и сервисом в рамках заявки.
7. Непрочитанные сообщения должны отображаться как числовой индикатор на вкладке.
8. Пользователь должен иметь возможность отменить активную заявку.
9. Автосервис должен иметь возможность отметить заявку как выполненную.
10. Система должна сохранять историю заявок и сообщений для обоих участников.
11. Пользователь и автосервис должны иметь возможность редактировать свой профиль.

Нефункциональные требования:
1. Время отклика API не должно превышать 2 секунд при нормальной нагрузке.
2. Приложение должно корректно работать на Android 8+ и iOS 13+.
3. Интерфейс должен корректно отображаться на экранах от 5 до 6.9 дюймов.
4. Данные пользователя не должны передаваться третьим лицам.
5. Системные пароли и токены должны храниться в зашифрованном виде.
6. Решение должно корректно работать в офлайн-ограниченном режиме для локального кэширования данных в пределах текущих сессий.

## 2.2 Графический интерфейс

### 2.2.1 Навигация

Навигация пользователя строится как линейная последовательность действий с тремя основными зонами:
- экран `Auth` — выбор режима авторизации/регистрации и роль пользователя;
- главный экран `Main` с нижним таб-баром: `Services`, `Requests`, `Profile`;
- переходы из `Services` на `SearchResults` и далее на бронирование конкретного сервиса.

Основные маршруты пользователя:
- `Auth` → `Main` при успешной авторизации/регистрации;
- `Main : Services` → `SearchResults` при выборе набора услуг;
- `SearchResults` → `Booking` при выборе даты/времени и переходе к отправке заявки;
- `Main : Requests` → `Chat` при выборе активной заявки;
- `Main : Profile` → редактирование личных данных.

Навигация автосервиса аналогична, но основное содержимое табов отличается:
- `Auth` → `Main` при входе сервиса;
- `Main : Services` — просмотр доступных услуг и, возможно, редактирование списка своих услуг;
- `Main : Requests` — список входящих заявок с переходом в карточку заявки и чат;
- `Main : Profile` — редактирование профиля автосервиса.

Важные элементы навигации:
- таб-бар обеспечивает быстрый доступ к основным режимам;
- детали заявки служат точкой перехода между списком и чатом;
- кнопка отправки заявки и выбор времени задают логическую ветку бронирования.

### 2.2.2 Экранная структура

Экран `Auth`
- цель: вход или регистрация пользователя/сервиса;
- ключевые элементы: форма логина/пароля, переключение роли, кнопки перехода на регистрацию/восстановление пароля, набор полей для начальной регистрации.

Экран `Services`
- цель: выбор перечня услуг для поиска автосервисов;
- ключевые элементы: перечень категорий услуг, выбор чекбоксов, кнопка поиска;
- результат: формирование списка параметров для запроса `/service/shippingAssistance`.

Экран `SearchResults`
- цель: отображение подходящих автосервисов после фильтрации по услугам;
- ключевые элементы: карточки сервисов с названием, адресом, рейтингом, основными услугами, кнопкой `Записаться`;
- дополнительные действия: выбор даты, запрос занятых слотов `/service/getBookedSlots`, переход к выбору времени и отправке заявки.

Экран `Booking` / детализация заявки
- цель: окончательное оформление записи;
- ключевые элементы: выбор даты, выбор времени, проверка доступности, ввод данных автомобиля и подтверждение записи;
- результат: создание заявки на `/service/sendApplication` и сохранение у пользователя `/user/addMyApplication`.

Экран `UserRequests`
- цель: просмотр списка заявок клиента;
- ключевые элементы: карточки заявок с сервисом, датой, временем, статусом и кнопкой перехода в чат;
- функционал: фильтрация по активным/завершённым, отмена заявки.

Экран `ServiceRequests`
- цель: просмотр списка входящих заявок автосервиса;
- ключевые элементы: карточки заявок с данными клиента, выбранными услугами, датой, временем и текущим статусом;
- функционал: переход в чат, отметка заявки как выполненной.

Экран `Chat`
- цель: обмен сообщениями между пользователем и автосервисом в рамках конкретной заявки;
- ключевые элементы: история сообщений, поле ввода текста, кнопка отправки, индикатор непрочитанных сообщений;
- особенности: оптимистичная вставка сообщения, регулярный polling для обновления истории, пометка прочитанных сообщений.

Экран `Profile`
- цель: просмотр и редактирование персональных данных или данных автосервиса;
- ключевые элементы: поля для имени, телефона, адреса, описания услуг, рабочего времени и кнопка сохранения;
- отличия ролей: для пользователя — данные автомобиля и контактные данные, для сервиса — список услуг, профиль компании, график работы.

Дизайн интерфейса:
- тёмная тема;
- основная палитра: фон `#1d1d1d`, карточки `#2a2a2a`;
- акцентные цвета: `#FFC107` для главных элементов, `#3a7bd5` для кнопок чата, `#ff3b30` для ошибок/удаления.

## 2.3 Архитектура

### 2.3.1 Ключевые архитектурные решения

1. клиент-серверное разделение;
2. REST API через Express;
3. MongoDB + Mongoose;
4. Redux Toolkit для состояния;
5. RTK Query для некоторых API-запросов;
6. `fetch` для сетевых вызовов;
7. polling вместо WebSocket для чата и уведомлений;
8. email-подтверждение регистрации через временный токен.

### 2.3.2 Компоненты архитектуры

Слой представления:
- React Native, TypeScript;
- Экран `Chat.tsx`, `Services.tsx`, `SearchResults.tsx`, `Auth.tsx`, `Registration*`, `Profile.tsx`.

Слой управления состоянием:
- `redux/store.ts`;
- `authTypeSlice.ts`;
- `registrationUserSlice.ts`.

Сетевой слой клиента:
- `src/api/baseUrl.ts`;
- `src/api/Users/*`;
- `src/api/AutoService/*`.

Сервер:
- `index.js`;
- роутеры `/user`, `/service`, `/chat`, `/verification`;
- контроллеры и модели;
- MongoDB.

### 2.3.3 API-интерфейсы

#### `/user`
- `POST /user/registrationUser` — регистрация пользователя по `tempToken` и паролю.
- `POST /user/loginUser` — авторизация пользователя.
- `GET /user/getServices` — список доступных услуг.
- `PUT /user/sendApplication` — отправка заявки от пользователя на сервис.
- `POST /user/addMyApplication` — сохранение заявки у пользователя.
- `PUT /user/updateApplicationStatus` — обновление статуса заявки у пользователя.
- `DELETE /user/cancelApplication` — отмена заявки.
- `PUT /user/addFavorite` — добавление в избранное.
- `PUT /user/removeFavorite` — удаление из избранного.
- `POST /user/getFavoriteServices` — получение избранных сервисов.

#### `/service`
- `POST /service/registrationAutoService` — регистрация автосервиса.
- `POST /service/loginAutoService` — авторизация автосервиса.
- `POST /service/getServiceById` — получение данных сервиса по ID.
- `POST /service/getBookedSlots` — получение занятых слотов.
- `POST /service/sendApplication` — создание заявки у сервиса.
- `PUT /service/updateDeclarationStatus` — изменение статуса заявки.
- `POST /service/getApplication` — проверка существования заявки.
- `POST /service/shippingAssistance` — поиск сервиса по услугам.
- `PUT /service/updateProfile` — обновление профиля сервиса.
- `PUT /service/addReview` — добавление отзыва.
- `POST /service/getReviews` — получение отзывов.

#### `/chat`
- `GET /chat/messages/:applicationId?login=...` — история чата, пометка входящих сообщений прочитанными.
- `POST /chat/send` — отправка сообщения.
- `POST /chat/unread` — количество непрочитанных сообщений по заявкам.

#### `/verification`
- `POST /verification/send-code` — отправка кода на email.
- `POST /verification/confirm-code` — подтверждение кода и выдача `tempToken`.
- `POST /verification/reset-password` — сброс пароля по email-коду.

## 4.2 Документация по установке и использованию

### 4.2.1 Руководство по сборке бэкенда

Требования:
- Node.js 18+
- MongoDB 6+

Шаги:
```bash
cd StoHelperRemasteredBackend-main
npm install
# создать .env с MONGO_URI
node index.js
```
Сервер по умолчанию доступен на `http://localhost:3000`.

### 4.2.2 Руководство по сборке фронтенда

Требования:
- Node.js 18+
- Expo CLI

Шаги:
```bash
cd StoHelperRemastered-master
npm install
# в src/api/baseUrl.ts указать URL бэкенда
npx expo start
```

### 4.2.3 Краткое руководство пользователя

Для пользователя:
1. Зарегистрироваться (получить код на email → подтвердить → указать пароль).
2. Выбрать услуги на вкладке `Услуги`.
3. Нажать `Найти` → выбрать сервис.
4. Выбрать дату и свободный слот времени.
5. Отправить заявку.
6. Открыть вкладку `Заявки` → написать сервису в чате.

Для автосервиса:
1. Зарегистрироваться как сервис.
2. Заполнить профиль и список услуг.
3. Открыть вкладку `Заявки` → работать с входящими заявками, отвечать в чате, отмечать `Выполнено`.
